# PostHog для TurboTears

PostHog показывает, какие страницы открывают, какие кнопки нажимают и где прерывают сценарий. Сам сайт уже считает эти события в своей базе и показывает их в админке. PostHog — дополнительный инструмент для исследования, а не условие работы сайта.

## Что готово

- Открытия публичных экранов → `$pageview`.
- Нажатия → `button_clicked`: экран, понятный код действия и раздел назначения.
- Начало сценария прогнозов → `prediction_view`, `prediction_start`.
- Подтверждённое сервером сохранение → `prediction_saved` (один аккаунт и этап — одно событие, повторные правки не увеличивают число).
- Псевдонимный ID браузера; нет email, Telegram ID, текста форм, параметров URL, содержимого прогноза или записи экрана.
- Отправка сервером через долговечную очередь. После ошибок отправка повторяется с задержкой; успех сайта не зависит от доступности PostHog. Очередь хранится до 30 дней. События до настройки PostHog не пересылаются задним числом.

Встроенная воронка считает сохранение по записи в базе прогнозов, а не по клику. В PostHog нажатие на отправку также не означает успешное сохранение.

## Выбранный вариант: PostHog Cloud

4 октября владелец выбрал облачный PostHog после проверки Ubuntu-сервера: 2 CPU, 2,9 GiB RAM (около 1 GiB доступно), около 5 GiB свободного диска. На этом сервере уже работают бот, web, nginx, Redis и Jenkins; собственный PostHog не запускался.

Владелец завершил регистрацию. Подключён EU-проект [TurboTears №293486](https://eu.posthog.com/project/293486/activity/events), адрес приёма — `https://eu.i.posthog.com`. DNS-поддомен для облачного варианта не требуется; созданный владельцем `analytics.f1hub.ru` этим подключением не используется.

После создания проекта взять **Project API key** в настройках проекта и добавить в серверный `.env`:

```dotenv
POSTHOG_HOST=https://eu.i.posthog.com
POSTHOG_PROJECT_KEY=ключ_проекта
```

Для проекта в US-регионе использовать `https://us.i.posthog.com`. Нужен публичный Project API key, а не личный Personal API key. Ключи не коммитить.

Код опубликован, серверное окружение настроено, пересоздан только web-сервис. Подключение подтверждено 4 октября 2026 года: в админке есть время успешной отправки, очередь и ошибки равны нулю; в Activity видны реальные открытия `/`, `/season` и нажатие `button_clicked`. Новые события собираются с 15:35 МСК, прежняя история не переносится в PostHog задним числом.

## Запуск собственного экземпляра

Нужны Ubuntu и домен, например `analytics.<ваш-домен>`, с A-записью на сервер. Официальный hobby-вариант рассчитан примерно на 300 тысяч событий в месяц; документация рекомендует 4 vCPU, 16 GB памяти и больше 30 GB диска. Он требует самостоятельного обслуживания и резервных копий. Стандартный установщик предназначен для отдельной VM: он занимает порты 80/443.

### Если используется существующий сервер бота

Сначала выполнить проверку, которая ничего не устанавливает и не меняет:

```bash
bash preflight.sh analytics.your-domain.example
```

Проверка показывает Ubuntu, CPU, свободную память и диск, занятые порты, контейнеры и DNS. На общем сервере ресурсы нужны дополнительно к боту, сайту и Jenkins. Если их мало, установку следует отложить либо выбрать другую инфраструктуру.

При достаточных ресурсах PostHog можно разместить отдельным Compose-проектом за существующим reverse proxy: отдельный поддомен и внутренний порт, без захвата публичных 80/443. Окончательные настройки зависят от того, nginx работает на хосте или в контейнере. `install-posthog.sh` для этого варианта не запускать; сначала требуется проверить текущую схему сервера и подготовить конфигурацию proxy. [Официальная инструкция по размещению за proxy](https://github.com/PostHog/posthog.com/blob/master/contents/docs/self-host/configure/running-behind-proxy.md).

### Если используется отдельная VM

1. Подготовить VM и DNS; убедиться, что порты 80/443 доступны.
2. Скопировать `install-posthog.sh` на VM и запустить:

   ```bash
   bash install-posthog.sh analytics.your-domain.example
   ```

   Скрипт загружает и запускает официальный установщик PostHog; его исходный код и инструкции приведены ниже. Установка оплачиваемого сервера этим файлом не выполняется.
3. Открыть полученный HTTPS-адрес, создать владельца и проект `TurboTears`. Пароль задаёт владелец сервера.
4. В настройках проекта скопировать **Project API key**. Personal API key не нужен.
5. В `.env` на сервере TurboTears добавить:

   ```dotenv
   POSTHOG_HOST=https://analytics.your-domain.example
   POSTHOG_PROJECT_KEY=ваш_ключ_проекта
   ```

6. Пересоздать web-контейнер, чтобы применить окружение:

   ```bash
   docker compose -f docker-compose-build.yml up -d --no-deps --force-recreate web
   ```

7. Открыть публичную главную, календарь, нажать быстрый доступ. В админке раскрыть «PostHog и сбор данных»: должны появиться настроенный статус и время успешной отправки. В PostHog проверить те же события в Activity. Статус «настроен» означает наличие адреса и ключа; успешное подключение подтверждается только временем отправки и событиями в PostHog.

Первый простой отчёт: `$pageview` по `path`. Второй: `button_clicked` по `action`, с разбивкой по `path`. Третий: воронка `prediction_view` → `prediction_start` → `prediction_saved`. Сохранение подтверждается сервером; отдельно можно сравнить его с `button_clicked`, где `action=prediction_submit`, чтобы найти неуспешные попытки.

## Эксплуатация

Резервируйте данные экземпляра по его документации и проверяйте восстановление. Не удаляйте Docker volumes при обновлении. Для остановки пересылки очистите оба параметра в `.env` и пересоздайте web-контейнер. Локальная аналитика продолжит работать. Недоставленные события будут ждать до включения или очистки очереди по сроку хранения.

Источники: [официальная документация self-hosting](https://posthog.com/docs/self-host), [официальный hobby installer](https://github.com/PostHog/posthog/tree/master/bin/hobby-installer), [Capture API](https://posthog.com/docs/api/capture). Версия инструкции проверена 4 октября 2026 года. Собственный экземпляр не развёрнут: проверка показала недостаток ресурсов, владелец выбрал облако.
