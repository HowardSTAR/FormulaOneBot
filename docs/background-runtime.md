# Фоновые задачи, восстановление и резервные копии

Приложение сохраняет общую бизнес-логику и SQLite. `bot` получает Telegram updates,
`web` обслуживает HTTP, `worker` владеет расписанием и обрабатывает постоянные
задания. Kafka, RabbitMQ, Celery и PostgreSQL для этого не требуются.

Локальный запуск из трёх терминалов после установки зависимостей:

```text
python -m app.migrate
python -m app.worker
python -m app.main
python run_web.py
```

Первый вызов выполняется один раз перед запуском остальных. В локальной среде
допускается автоматическое применение миграций. В production Compose устанавливает
`DATABASE_AUTO_MIGRATE=false`: отдельный `migrate` должен успешно завершиться до
запуска приложений. `schema_migrations` хранит применённые версии. Существующая
идемпотентная схема сохранена как версия 1, новые изменения — отдельная версия 2.
Блокировка ОС исключает одновременное выполнение миграций и двух воркеров на
общем локальном диске; при аварийном завершении ОС освобождает блокировку.

**Восстановление расчётов.** POST аналитического прогноза возвращает `202` и ID
сохранённого задания. HTTP-процесс его не выполняет. Воркер забирает работу
транзакционно, сохраняет входной снимок перед вычислением и публикует результат
только с действующим токеном владения. Устаревший исполнитель не может затереть
результат другого. При штатной остановке захват освобождается сразу, при аварии
истекает через четыре минуты. Временные ошибки повторяются с увеличением паузы
до пяти минут. Ожидание ограничено 24 часами, каждый запуск — тремя минутами.

История и доступные сессии отбираются по первоначальному времени запроса.
После сохранения снимка повторы не запрашивают входные данные заново. После
начала целевой сессии новый прогноз не сохраняется: восстановление не должно
превращать прогноз в расчёт по уже известному результату. Такой запрет является
окончательным исходом, а не просьбой вручную повторить работу.

Это отличается от отправки во внешний сервис: неоднозначный ответ Telegram
по-прежнему сохраняется как `unknown` без слепой повторной отправки. Сохранение
этой политики предотвращает автоматическое дублирование потенциально принятого
сообщения. Проверка такого случая остаётся в существующей админке.

**Резервное копирование.** При старте worker и раз в сутки создаётся SQLite online
backup в `data/backups`. Копия восстанавливается во временную БД и проходит
`integrity_check` и проверку внешних ключей. Сжатый `.db.gz` проверяется повторно.
Manifest содержит имя, размер, SHA-256 и время проверки. Файл без готового
manifest не считается опубликованной резервной копией.

```dotenv
BACKUP_DIR=/app/data/backups
BACKUP_KEEP=7
```

Удаляются только подтверждённые внешние копии старше последних `BACKUP_KEEP`.
Непереданные снимки не удаляются, пока ПК выключен или недоступен. Их очередь
может занять место на сервере; свободное место и количество ожидающих копий
показываются в административной сводке. Это сознательная политика сохранности.

Загрузчик `scripts/backup_pull.py` работает на ПК через уже настроенный SSH.
Он не создаёт недоступный каталог при каждом запуске: ждёт возвращения заданного
пути. Перед подтверждением на сервере проверяет SHA-256, размер и восстановление
локальной копии. Прерванная загрузка не публикуется, потерянное подтверждение
не заставляет повторно скачивать уже проверенный файл.

```powershell
.\scripts\install-backup-pull.ps1 -Destination 'D:\backup - f1' -Source 'user@server' -Identity 'C:\path\backup-key'
```

Установщик один раз создаёт указанный каталог и задачу Windows `TurboTears backup
pull`: каждые 15 минут во время пользовательского сеанса, без видимого окна.
Задача запускается через `pythonw.exe`; дочерние SSH и SCP запускаются с
`CREATE_NO_WINDOW` и отключённым вводом, чтобы не открывать терминал и не забирать фокус.
`StartWhenAvailable` позволяет продолжить после пропущенного запуска. Удаление
задачи: `Unregister-ScheduledTask -TaskName 'TurboTears backup pull'`.
Для восстановления распаковать архив в отдельный каталог и выполнить
`python -c "from app.utils.sqlite_backup import verify_backup; verify_backup('copy.db.gz')"`.
Не заменять работающую БД без остановки пишущих процессов и отдельного плана
переключения. Автоматического отката пользовательских данных при релизе нет.

**Контроль выполнения.** В административной сводке доставки доступны heartbeat
воркера, успешные/ошибочные выполнения задач, ожидающие расчёты, проверенные
бэкапы, подтверждённые переносы на ПК и свободное место. Heartbeat старше
90 секунд означает отсутствие свежего сигнала. Статус завершения периодической
функции не является подтверждением доступности каждого внешнего провайдера:
некоторые интеграции намеренно используют сохранённые данные при сбое.

```text
python -m app.worker --check
```

Проба читает сохранённый heartbeat и не запускает обработку. У бота также есть
heartbeat цикла событий; он не доказывает доступность Telegram. Веб `/health`
проверяет доступность SQLite. Эти проверки не требуют, чтобы все внешние API
были онлайн. Контроль полного выключения сервера должен находиться за его
пределами; внутренний heartbeat после потери сервера не отправит уведомление.

**Релиз.** Обновлённый `deploy-verified.sh` сохраняет копию БД, останавливает
предыдущего владельца расписания, выполняет миграции, запускает bot/web/worker и
проверяет состояние. При неудаче возвращает предыдущий образ. При первом
внедрении worker откат не запускает его рядом со старым ботом-планировщиком.
Миграция этого релиза добавляет таблицы и столбцы и сохраняет совместимость со
старым образом. Для будущих миграций такая совместимость требует отдельной
проверки. Compose-файл и установленный CI-скрипт должны обновляться вместе.

**Проверки.** `tests/test_background_runtime.py` проверяет восстановление,
конкуренцию, снимки, бэкапы и недоступный диск; `deploy/jenkins/test_deploy.py` —
порядок релиза и откат через фиктивный Docker, без изменения сервера.

Для проверки временного сбоя по настоящему HTTP используется локальная
синтетическая модель MRData, основанная на формате, который уже читает проект.
Она не является официальным mock Jolpica и не проверяет актуальные данные API.
Поиск облачного mock не выполнялся: тест не требует облачного workspace.

```text
postman simulation run postman/simulations/forecast-recovery.sim.yaml --port 4900 --no-history
```

Во втором терминале задать `FORECAST_SIMULATION_URL=http://127.0.0.1:4900` и
запустить `python -m pytest tests/test_forecast_simulation.py -q`. Тест выполняет
настоящие HTTP-запросы, получает 503, возвращает провайдер в рабочее состояние
и проверяет завершение того же задания без повторного POST пользователя.

**Внедрение 20 октября 2026.** Рабочий образ имеет версию
`87ac321-runtime-20261020`. Перед переключением проверены миграция отдельного
снимка рабочей БД, восстановление сжатого архива и изолированные API/worker
с отключённой внешней сетью. После переключения bot, web и worker имеют статус
healthy, публичный `/health` отвечает `database=ready`, Telegram getMe доступен
из worker. Зарегистрировано 19 периодических задач. Существующие сетевые
переопределения сервера распространены на worker.

Задача Windows установлена для `D:\backup - f1`, интервал 15 минут. Проверены
две рабочие копии примерно по 247 МиБ; вторая получена установленной задачей
Windows с результатом 0. Обе подтверждены на сервере после локальной проверки
восстановления. Исходные настройки Compose, CI и сетевых переопределений
сохранены в `/root/f1hub-runtime-release-20261020`; предыдущий образ сохранён
для отката. Рабочие данные не откатывались.

Проверки кода: 1564 backend-теста прошли, два opt-in случая пропущены;
HTTP-симуляция проверена отдельно. Прошли 160 frontend-тестов, TypeScript,
проверка изменённых компонентов ESLint, сборка фронтенда и 10 тестов деплоя
и отката. После финальных изменений выполнено ещё 50 целевых проверок.
